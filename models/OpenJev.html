OpenJev (DiffusionGemma 26B-A4B)

OpenJev is a local server that accepts the same choice questions as the Jev API. In this project it runs a four-bit MLX build of DiffusionGemma 26B-A4B. The confidence value comes from the server and equals one minus the normalized entropy of the probabilities.

01

About this model

In this project the model is registered as OpenJev, and its code is in classifiers/OpenJev/.

There is no hard adapter limit on the number of labels. Practical capacity is still constrained by context length, label-description truncation, memory, runtime and model quality, so validate large label sets separately.

03

Getting the model

The official page is github.com/razorback16/openjev. The setup script pins exact revisions in classifiers/OpenJev/setup.sh or classifier.py. Use the setup script instead of downloading the latest revision by hand, because a different revision can give different results.

shell
./run setup OpenJev

For this entry, ./run setup installs only the client. The model runs in a separate server. The server setup clones the OpenJev repository into server/src/ and downloads the MLX model named by OPENJEV_MLX_MODEL.

shell
classifiers/OpenJev/server/setup.sh   # once
classifiers/OpenJev/server/serve.sh   # start the server, leave it running

04

Installing from a clean checkout

shell
cd /path/to/Classification
runner/setup.sh        # the runner's own environment
cp .env.example .env    # then edit the settings you need
./run list
./run setup OpenJev

The reference platform is macOS on Apple Silicon. Requirements for memory, GPU, Ollama, servers and API keys differ between entries, and ./run list states what is missing for each one. If a check fails during setup, fix the cause instead of skipping the check. Keep API keys in .env. Do not put them in HTML files or commit them.

05

Sending data and reading results

Input format

  • Labels: a Python dict that maps each label ID to a short description. The ID is what the model returns. The description is what the model reads, so it should say clearly what belongs in that label.
  • Instruction: one question that tells the model what decision to make, for example What is the topic of this news article?.
  • Text: one string per call to predict, or a list of strings for predict_many, which batches them.

The benchmark builds the labels from the task manifest in data/tasks/. For your own labels, pass your own dictionary. Use IDs without spaces, because the evaluator writes one column named p_<id> per label.

Calling it from Python

Run Python from the entry's folder with its own environment. PYTHONPATH must point at shared/, because the adapter imports the task loader from there.

shell
cd classifiers/OpenJev
PYTHONPATH=../../shared .venv/bin/python my_script.py
python
from classifier import OpenJevClassifier

labels = {
    "world": "International news, politics, government, conflicts, diplomacy, elections",
    "sports": "Sports events, athletes, teams, games, tournaments, leagues",
    "business": "Companies, markets, economy, finance, earnings, trade, oil prices, mergers",
    "sci_tech": "Science, technology, computing, internet, software, space, health research",
}
instruction = "What is the topic of this news article?"

clf = OpenJevClassifier(labels, instruction)

p = clf.predict("Stocks rallied after the central bank decision.")
print(p.label)          # the label ID with the highest score
print(p.confidence)     # a number from 0 to 1
print(p.probabilities)  # one score per label ID

many = clf.predict_many(["First text.", "Second text."])  # Predictions, in order

Output format

predict returns a Prediction object with three fields:

  • label: the chosen label ID. It is always a label with the highest score.
  • confidence: a number from 0 to 1. For this entry it is defined as: server's 1 - normalized entropy. The confidence field is a separate server score and should not be interpreted as the selected label's probability.
  • probabilities: a dict from every label ID to the service's per-label score. Confidence type: Separate score.

What goes over the wire

The Python class sends one HTTP request per text to the server at http://127.0.0.1:8080. The request is a "choice question" in the Jev format: the text goes in state, and the labels go in criteria as ID and description pairs. Before a run, the adapter checks the server with GET /v1/models.

http
POST http://127.0.0.1:8080/v1/systemone
Content-Type: application/json
Authorization: Bearer <key>   (only when an API key is set)

{
  "model": "openjev-latest",
  "state": "Stocks rallied after the central bank decision.",
  "questions": {
    "label": {
      "type": "choice",
      "instructions": "What is the topic of this news article?",
      "criteria": {
        "world": "International news, politics, government, conflicts, diplomacy, elections",
        "sports": "Sports events, athletes, teams, games, tournaments, leagues",
        "business": "Companies, markets, economy, finance, earnings, trade, oil prices, mergers",
        "sci_tech": "Science, technology, computing, internet, software, space, health research"
      }
    }
  }
}

The server replies with the chosen option, its confidence and the probability of every option (the numbers below are from this entry's recorded sample):

json
{
  "answers": {
    "label": {
      "choice": "business",
      "confidence": 0.9962,
      "probabilities": {
        "business": 0.9994,
        "sports": 0.0004,
        "sci_tech": 0.0001,
        "world": 0.0001
      }
    }
  },
  "usage": {"input_tokens": ..., "output_tokens": ...}
}

Failed requests (connection errors, HTTP 429 and server errors) are retried with a growing delay. You can call the server from any language with the same JSON.

What it learns from the task

Approach in the score reports: zero-shot. Nothing is fitted on task data: it decides from the label names and descriptions alone.

The data preparation, sampling and calibration sample sizes are the same for every entry: see What every entry shares.

08

Training and adaptation

No fine-tuning

This adapter uses a released, already trained checkpoint and applies it to the label set. No training is part of the benchmark.

If the results are poor on your data, first improve the label names and descriptions in the manifest. Fine-tuning is possible but is outside this adapter. If you do it, use the training procedure from the official project page, keep the test data out of training, use a train and validation split, prefer a parameter-efficient adapter for models with billions of parameters, calibrate probabilities on held-out train data, and register the new checkpoint as a separate entry. Do not replace the pinned release, because earlier results could then no longer be reproduced.

When something goes wrong

  • ./run OpenJev --dry-run shows the arguments the runner passes to this entry.
  • Run ./run setup OpenJev again after changing Python or dependencies.
  • "Cannot reach" or "not ready" means the server is not running or is still loading the model.
