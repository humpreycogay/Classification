Models/042/verdict_shortlist

Verdict (ModernBERT 151M) + shortlist of 24

Verdict is a decision model with 151 million parameters: ModernBERT-base with a GLiClass head. It is loaded with the gliclass package. It always adds an "insufficient evidence" option, divides the logits by a temperature chosen for the number of options, and accepts 2 to 24 labels.

01

About this model

In this project the model is registered as verdict_shortlist, and its code is in classifiers/verdict/. This entry passes --shortlist 24 to the evaluator. Other entries that use the same folder: verdict.

This is a two-stage entry. BGE-M3 first compares the text with every label description and keeps the 24 closest labels. The model then chooses among those 24. If the correct label is not in the shortlist, the model cannot choose it, so the shortlist's recall is the highest accuracy this entry can reach.

How the main model works

After the shortlist stage (see Sending data and reading results), the main model works as below, on the 24 kept labels only.

03

Getting the model

The official page is huggingface.co/heman10x/rlcd-modernbert-151m. The setup script pins exact revisions in classifiers/verdict/setup.sh or classifier.py. Use the setup script instead of downloading the latest revision by hand, because a different revision can give different results.

shell
./run setup verdict_shortlist

The setup script creates classifiers/verdict/.venv, installs requirements.txt, downloads the pinned weights, and runs the adapter's checks where it has them (probe texts, and for some entries a comparison of GPU and CPU scores).

Ollama models are pulled with ollama pull bge-m3:567m. The setup script does this when Ollama is running.

Installing from a clean checkout

shell

cp .env.example .env    # then edit the settings you need

The reference platform is macOS on Apple Silicon. Requirements for memory, GPU, Ollama, servers and API keys differ between entries, and ./run list states what is missing for each one. If a check fails during setup, fix the cause instead of skipping the check. Keep API keys in .env. Do not put them in HTML files or commit them.

05

Sending data and reading results

How the two stages work

For each text, BGE-M3 (through Ollama) ranks all labels by cosine similarity between the text and the label descriptions. The 24 closest labels are passed to the model as an ordinary label set. The output dictionary still has every task label: labels excluded by the shortlist are assigned 0 as placeholders, and the remaining values are the main model's normalized scores within the shortlist. The input and output formats of the model itself are described on the verdict page.

The two stages at a glance

Calling it from Python

The benchmark evaluator does both stages for you. To do them in your own code, build a Shortlister from shared/shortlist.py, then pass each text's shortlisted labels to predict_shortlisted, which every shortlist-capable classifier has.

shell
cd classifiers/verdict
BENCHMARK_TASK=banking77 PYTHONPATH=../../shared .venv/bin/python my_script.py
python
from task import current_task
from shortlist import Shortlister
from classifier import VerdictClassifier

task = current_task()  # run with BENCHMARK_TASK=banking77
labels = {s["id"]: s["description"] for s in task.labels}  # all 77 intents
k = 24

shortlister = Shortlister(task, k)  # stage 1: embeds the 77 label texts with bge-m3 (Ollama)
clf = VerdictClassifier(dict(list(labels.items())[:k]), task.instruction)  # stage 2, built for k labels

text = "I ordered a new card two weeks ago and it still has not arrived."
keep = shortlister.top_k([text])[0]  # the k label IDs closest to the text
p = clf.predict_shortlisted([text], [{l: labels[l] for l in keep}])[0]
print(keep)
print(p.label, p.confidence)

Running it on the benchmark

shell
./run verdict_shortlist --task banking77 --n 200

The run metadata records the shortlist's recall: the share of texts whose correct label was kept, measured on the calibration split and on the test sample. That share is the highest accuracy the entry can reach.

Benchmark output

The benchmark evaluator writes a CSV file of predictions to the entry's results folder. It has one row per test text and these columns: sample_id, text, label (the true label), pred, confidence, and one p_<label> column per label. runner/validate.py checks that the rows match the expected sample, that every label is known, that each row's probabilities sum to 1, and that pred has the highest probability.

06

How the benchmark prepares data

Every entry receives the same data in the same way. This makes the results comparable.

  1. shared/task.py loads the task manifest, data/tasks/ag_news.json or data/tasks/banking77.json.
  2. On first use it downloads the CSV files named in the manifest, if they are not present, and verifies their SHA-256 checksums.
  3. The raw columns are converted to exactly two: text and label. For AG News the text is the title and the description joined as {title}. {description}. Banking77 uses its text column.
  4. The runner draws the same label-balanced test sample for every entry, chosen by --n and --seed.
  5. The adapter receives the label IDs, names, descriptions and the task instruction. Supervised models fit on the train split. Zero-shot models fit nothing that changes their decision. A few (confidence type task-calibrated) fit one confidence temperature on a fixed labeled sample drawn from the train split: their accuracy remains zero-shot, but their confidence and calibration metrics are task-calibrated.

07

Running the benchmark

shell
./run verdict_shortlist --task banking77 --n 200

--n 0 runs the whole test split. --seed N draws a different but reproducible sample. --dry-run prints the resolved command without running it. Options for the adapter itself go after --.

Inside the full benchmark

shell
./run all --task banking77 --only verdict_shortlist
./run report --task banking77

The first command runs only this entry and then rebuilds the report. The second rebuilds the report from results that already exist.

08

Training and adaptation

No fine-tuning

This adapter uses a released, already trained checkpoint and applies it to the label set. No training is part of the benchmark.

If the results are poor on your data, first improve the label names and descriptions in the manifest. Fine-tuning is possible but is outside this adapter. If you do it, use the training procedure from the official project page, keep the test data out of training, use a train and validation split, prefer a parameter-efficient adapter for models with billions of parameters, calibrate probabilities on held-out train data, and register the new checkpoint as a separate entry. Do not replace the pinned release, because earlier results could then no longer be reproduced.

09

Reading the results

Accuracy tells you how often the top label was correct. It does not tell you which labels the model confuses. For that, the report also shows a confusion matrix, scores per class, calibration and error analysis, latency, memory use, and selective prediction (accuracy when only confident answers are kept). Compare two runs only when the task, sample size, seed and model revision are the same.

A high confidence value does not guarantee a correct answer. For this entry, confidence is defined as: max p over the shortlist.

When something goes wrong

  • ./run list --task ag_news shows whether the entry is ready and, if not, why.
  • Run ./run setup verdict_shortlist again after changing Python or dependencies.
  • Check .env.example for this entry's host, model, device, key and context settings.
  • ./run verdict_shortlist --dry-run shows the arguments the runner passes.
  • ModuleNotFoundError: No module named 'task' (or 'training') when running classifier.py directly means PYTHONPATH=../../shared is missing.
  • "Ollama not reachable" means Ollama is not running at the configured host. "not pulled" means the model tag must be pulled first.
  • Out-of-memory errors, truncated options and unreachable services are setup problems, not measures of model quality.
