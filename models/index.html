Text Classification Benchmark and Guide

A benchmark and a hands-on guide to text classification. 44 classifiers, from TF-IDF baselines and networks trained from scratch to fine-tuned encoders, zero-shot models and LLMs, are run on the same AG News and Banking77 test sets. Each model page explains what the model is, what it needs, how to run it and call it from Python, and how to read its results; the trained entries walk through training from scratch and fine-tuning step by step. Start with Get started, or go straight to the model table.

01

Get started

Everything on this site can be reproduced from the repository: the setup scripts download each model, the benchmark datasets are downloaded on first use and checked against a pinned checksum, and the runner writes the same reports you see here from your own results.

Requirements. macOS on Apple Silicon is the reference machine (MPS / MLX GPU); many PyTorch entries also run on CUDA or CPU. Python 3.12 or newer (SemIf, Nimble and the OpenJev server need 3.12 specifically). Some entries also need Ollama, an API key or a remote GPU server; each model page lists what it needs.

shell
git clone https://github.com/humpreycogay/Classification Classification
cd Classification
runner/setup.sh              # the runner's own environment (once)
cp .env.example .env         # model choices, devices and API keys; the defaults work for local entries
./run list                   # every classifier: ready to run, or what it still needs
./run setup tfidf_svm        # one entry: virtualenv, dependencies, model download
./run tfidf_svm              # 200 AG News articles; --task banking77, --n 1000, --dry-run
./run report                 # rebuild reports/ag_news.html from your results

To classify a single text with an entry that is set up:

shell
cd classifiers/tfidf_svm
PYTHONPATH=../../shared .venv/bin/python classifier.py "Stocks rallied after the central bank decision."

./run all runs every entry that is set up and builds the comparison report. tfidf_svm is a good first entry: it needs no GPU and runs in under a minute.

02

What a classifier does

A text classifier reads a piece of text and assigns it one label from a fixed list. The list is decided in advance. In this project there are two lists: four news topics for AG News (World, Sports, Business, Science/Technology) and 77 customer intents for Banking77, such as card_arrival or lost_or_stolen_card.

Every classifier here returns the same three things for each text: the chosen label, a confidence value between 0 and 1, and a score for every label in the list (a probability estimate for most entries; see What the confidence numbers mean). Because the output is the same, the models can be compared on the same test texts with the same measures.

03

What a System One model is

Many of the models in this guide describe themselves as System One models. The name comes from psychology, where System 1 refers to fast, automatic judgments and System 2 to slow, step-by-step reasoning. In this field it names a model built to make one decision quickly. It receives a situation (the text, called the state) and a closed set of options, and it returns one probability per option, usually from a single forward pass.

A System One model does not write an explanation, and it does not generate an answer word by word as a chat model does. This makes it faster and cheaper per decision, and its output can always be parsed: it is one of the given options, never free text. TypeSafe's Jev API defined the request format, called /v1/systemone, in which a choice question carries an instruction and a set of criteria (the options with descriptions). OpenJev, djev and Winnow serve the same format, and models such as d1, Decider, Nimble, Kev and CLM were trained for this kind of decision.

A chat model can be used in the same way, as the llmqwen entry shows, by listing the options with letters and reading the probability of each letter. The difference is that a System One model is trained for the decision, while a chat model is prompted into it.

Other ways to classify text

System One models are one approach among several. Text classification is an older field than these models, and the other approaches remain useful:

  • Classic machine learning. Word and character features weighted with TF-IDF, passed to logistic regression, a linear SVM or Naive Bayes. These train in seconds on a CPU and need labelled examples.
  • Embeddings with a small classifier. An embedding model turns each text into a vector, and a simple classifier is trained on those vectors.
  • Fine-tuned custom models. An encoder such as BERT or ModernBERT, trained on your own labelled data for your own labels. When enough labelled data exists, this is often the most accurate and cheapest option to run.
  • Other zero-shot methods. Natural language inference models and prompted chat models, which need no labelled data.

This project focuses on Jev-style decision models because comparing them is its purpose. The other approaches are included as reference points: the TF-IDF and embedding baselines are trained on each task's train split, and on AG News they are among the most accurate entries. If your task has labelled data, compare against them before choosing a System One model.

05

What every entry shares

Every entry receives the same data in the same way, which is what makes the results comparable.

  1. shared/task.py loads the task manifest, data/tasks/ag_news.json or data/tasks/banking77.json.
  2. On first use it downloads the CSV files named in the manifest, if they are not present, and verifies their SHA-256 checksums.
  3. The raw columns are converted to exactly two: text and label. For AG News the text is the title and the description joined as {title}. {description}. Banking77 uses its text column.
  4. The runner draws the same label-balanced test sample for every entry, chosen by --n and --seed.
  5. The adapter receives the label IDs, names, descriptions and the task instruction. Supervised models fit on the train split. Zero-shot models fit nothing that changes their decision. A few (confidence type task-calibrated) fit one confidence temperature on a fixed labeled sample drawn from the train split: their accuracy remains zero-shot, but their confidence and calibration metrics are task-calibrated.
TaskLabelsTextCalibration sampleSupervised sample
AG News4 topicstitle and description100 train rows per label1,000 rows per label
Banking7777 intentscustomer message5 train rows per label30 rows per label

To use your own data, copy a manifest in data/tasks/, give the train and test files or URLs with their checksums, map every raw label to an ID, and write a short description for each label that separates it from the others. Only single-label classification is supported.

Benchmark output

The benchmark evaluator writes a CSV file of predictions to the entry's results folder. It has one row per test text and these columns: sample_id, text, label (the true label), pred, confidence, and one p_<label> column per label. runner/validate.py checks that the rows match the expected sample, that every label is known, that each row's probabilities sum to 1, and that pred has the highest probability.

Running options

--n 0 runs the whole test split. --seed N draws a different but reproducible sample. --dry-run prints the resolved command without running it. Options for the adapter itself go after --. ./run all runs entries and then rebuilds the report; ./run report rebuilds it from results that already exist.

Reading the results

Accuracy tells you how often the top label was correct, not which labels a model confuses; the report adds a confusion matrix, per-class scores, calibration, latency, memory and selective prediction. Compare two runs only when the task, sample size, seed and model revision are the same. A high confidence value does not guarantee a correct answer.

Common problems

  • ./run list --task ag_news shows whether each entry is ready and, if not, why.
  • Run ./run setup <name> again after changing Python or dependencies.
  • .env.example lists each entry's host, model, device, key and context settings.
  • ModuleNotFoundError: No module named 'task' (or 'training') when running classifier.py directly means PYTHONPATH=../../shared is missing.
  • Out-of-memory errors, truncated options and unreachable services are setup problems, not measures of model quality.

06

How the models differ

Zero-shot models decide without fitting their weights or label ranking on task examples. They read the label descriptions and decide. Changing the labels needs no training, so the quality of the descriptions matters. Some use labeled training examples solely to fit a confidence temperature; their accuracy remains zero-shot, but their confidence and calibration metrics are task-calibrated (see What the confidence numbers mean).

In-domain checkpoints are released models whose training data includes a bundled task. Their scores on that task are reported separately, because they have seen similar texts before.

Classical supervised baselines, such as TF-IDF with logistic regression or embeddings with a linear classifier, are fitted on the task's own train split. They show what a small, conventional model reaches with labelled data.

Fine-tuned encoders are pre-trained language models adapted to the task's train split, and models trained from scratch learn only from that split, starting from random weights.

The score reports use these five approaches to group results, because a ranking across them compares different amounts of task data as much as different models. Entries that run on a remote service are flagged separately, because their timings include the network.

Shortlist variants handle tasks with more labels than a model accepts. An embedding model first keeps the most similar labels, and the main model chooses among them.

07

What the confidence numbers mean

Every entry returns a confidence value and a score per label, but these numbers do not all mean the same thing. Four concepts are easy to mix up:

Raw score or margin
Useful for ordering labels, for example an SVM margin or a similarity. Not a probability, and not on a 0 to 1 scale.
Normalized score
Non-negative and sums to 1 over the labels, for example a softmax of raw scores. It looks like a probability but may still be badly calibrated.
Calibrated probability estimate
Checked against data so that, on similar texts, a stated 0.8 is right about 80% of the time. Calibration holds only for data like the data it was checked on.
Separate confidence score
A number a service computes on its own terms, for example 1 minus the normalized entropy. Useful for ranking predictions, but not the selected label's probability.

Each model page shows one of these confidence types as a badge, and the score reports use the same terms:

08

How to choose a model

The table lists every entry. To narrow it down for a deployment, answer these questions in order. Each answer points to a group in the table, not to a single best model: the score reports show how the entries in a group compare on each task.

  • Do you have labeled data for your task?
    • Yes, and you want the smallest and fastest option: supervised baselines (TF-IDF, embeddings).
    • Yes, and you can train an encoder: fine-tuned encoders; the from-scratch networks are a cheaper reference.
    • No: zero-shot models. Check models trained on benchmark data separately: their scores on those tasks are in-domain.
  • Does your task have more labels than the model accepts? See the Labels column; use the shortlist variants, whose accuracy is capped by the shortlist's recall.
  • May the text leave the machine? If not, filter the table for Local; only entries marked as remote send text to a service.
  • Do you need meaningful confidence, for example to auto-accept predictions? Prefer entries whose confidence type is calibrated, and validate the calibration and the threshold on your own data.
  • Memory, latency or cost limits? Each score report ranks the entries by time per item, interactive latency, memory and cost, and shows the accuracy-versus-speed frontier.

09

Training from scratch or fine-tuning

Two words get mixed up when people talk about building their own classifier. Training from scratch starts from random weights, so the task's train split must teach the model everything: which words matter, which are similar, and which label they point to. Fine-tuning starts from a model that was already pre-trained on huge amounts of text and only teaches it the labels. With limited labeled data, fine-tuning a suitable pretrained encoder often trains more efficiently and performs better than training a comparable neural encoder from random initialization; training a small network from scratch is cheap, fast, and the best way to learn how neural classifiers work.

The three entries in the Trained from scratch group are small neural networks trained from random weights. They differ only in how many word vectors become one text vector: a fastText-style average, a CNN that detects phrases, and a BiLSTM that reads in order. A small Transformer is deliberately not among them: trained from scratch on data this size it gains little over these, and Transformers pay off when they are pre-trained and then fine-tuned.

The Fine-tuned encoders group takes that route: two released pre-trained encoders, ModernBERT-base and DeBERTa-v3-base, each fine-tuned on the task's train split. Their pages explain the concepts, the training procedure and how to reproduce it step by step.

Worth knowing: models not benchmarked

The two models below are relevant to this comparison, and an adapter for each exists in classifiers/. They were not benchmarked, because their hardware requirements are beyond the Apple Silicon Mac with 32 GB of memory used for every other result. Without a run there are no accuracy, speed or memory figures, no recorded sample, and no verified setup steps, so this guide does not give them a model page.

ModelWhat it isWhy it was not run
Dexy-Decision-9B
Patrick-18 · classifiers/dexy/		An experimental 9B decision checkpoint. A verbalizer head scores 2 to 256 options in one pass and returns a probability for each, with the release's own temperature.The release is built and verified for Linux with an NVIDIA GPU (CUDA). Its BF16 weights are 17.9 GB, more than half of the Mac's memory, and it has not been verified on Apple MPS. The setup script refuses to download it unless DEXY_ALLOW_EXPERIMENTAL=1 is set.
djev with DiffusionGemma 26B-A4B
djev (server), Google (model) · classifiers/djev/		A decision server that runs DiffusionGemma 26B-A4B in BF16 with vLLM and answers the same /v1/systemone choice questions as the Jev API.The BF16 weights alone are about 52 GB. The deploy script needs a Linux host with an NVIDIA B200 GPU, Docker, the NVIDIA Container Toolkit and about 128 GB of RAM, reached through an SSH tunnel. No such host was available.

Dexy is worth studying as the largest open decision checkpoint in this family. It shows how a verbalizer head turns a 9B language model into an option scorer. djev is the reference way to serve DiffusionGemma for decisions. The same model can be measured on a Mac through OpenJev, which serves it in four-bit MLX, accepts the same requests, and has results in the reports. The difference between the two is the precision: four-bit weights instead of BF16.

Both entries remain in runner/apps.py. With the right hardware, they run like any other entry, and their results would appear in the reports.
